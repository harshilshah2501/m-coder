# Dependency Reproducibility Hardening

Short reference for addressing audit caveats on Python dependency pinning and container image reproducibility. **This is a planning and documentation note.** Do not mass-edit dependency versions or refactor build systems without an explicit implementation step.

**Source:** [docs/runtime/verification/SYSTEM_DEPENDENCY_SUPPLY_CHAIN_AUDIT.md](../runtime/verification/SYSTEM_DEPENDENCY_SUPPLY_CHAIN_AUDIT.md) (PASS WITH CAVEAT).

### Container default image

| Surface | Value | Location |
|---------|--------|----------|
| Sandbox default image | `python:3.12-slim` (no digest) | `runtime/sandbox/container_sandbox_driver.py` — `DEFAULT_IMAGE` |

The tag can be overwritten by the registry; there is no digest pin (`@sha256:...`). Callers can pass a different `image`; the default is used when none is supplied (e.g. `SandboxExecutor` / `ContainerSandboxDriver` init).

**Other container references:** `runtime/rag/docker/docker-compose.yml` uses `qdrant/qdrant:latest` and `neo4j:latest` for local RAG services; those are out-of-band to the governed execution sandbox and are not in scope for this note’s “default container” hardening.

## 2. Recommended minimal path

### Python: lockfiles or pinned production requirements

- **Option A — Lockfiles:** Introduce a lockfile per environment (e.g. `runtime/rag/requirements.lock` and/or `ml/training/requirements.lock`) generated by `pip-tools` (`pip-compile`) or equivalent, and document install as `pip install -r requirements.lock`. Keep existing `requirements.txt` as the source of lower bounds for `pip-compile` if using pip-tools.
- **Option B — Pinned production requirements:** Maintain a separate production manifest (e.g. `requirements-prod.txt` or `requirements.pinned.txt`) with exact versions (`==`) for runtime or training, and use it only where reproducible builds are required. Do not blindly change versions in existing `requirements.txt`; do it in a dedicated step with review.

Prefer one approach per surface (RAG vs training) to avoid mixed patterns. Do not change Python dependency versions in the same change as adding this doc.

### Container: digest-pinned default image

- **Goal:** Use a digest-pinned image for the sandbox default so that `DEFAULT_IMAGE` resolves to an immutable reference.
- **Approach:** Set `DEFAULT_IMAGE` to the form `python:3.12-slim@sha256:<digest>`. Obtain the digest from the registry (e.g. `docker manifest inspect python:3.12-slim` or Docker Hub API) for the image you intend to pin; update the digest when intentionally upgrading the base image.
- **Where:** `runtime/sandbox/container_sandbox_driver.py` — single constant `DEFAULT_IMAGE`. Call sites that pass `image=` override this; default is used when no image is passed.

## 3. Proposed container change (do not apply automatically)

A single, low-risk change is to replace the literal in `container_sandbox_driver.py`:

- **Current:** `DEFAULT_IMAGE = "python:3.12-slim"`
- **Proposed:** `DEFAULT_IMAGE = "python:3.12-slim@sha256:<digest>"` with `<digest>` taken from the official image for the chosen tag.

The repo does not currently document digest-pinning as a standard; this document defines the *recommended* behavior. Apply the digest pin in a separate, explicit implementation step (e.g. “Pin sandbox default image by digest”) with a single commit that updates only `DEFAULT_IMAGE` and, if desired, a short comment that the image is digest-pinned for reproducibility.
