# M3.11 — Container Sandbox Runtime

## Objective

Implement a **container-based sandbox runtime** as a backend under the existing M3.10 driver abstraction. Goals:

- Stronger execution isolation than process-only mode.
- Plan-Gate still decides; runtime still owns control flow; ledger contracts unchanged.
- Sandbox backend is isolated but not authoritative; local process backend still works unchanged.

## Design

### Container backend

- **ContainerSandboxDriver(BaseSandboxDriver)**: `driver_name = "container"`. Implements `run(...)` and `validate_only(...)` using the existing driver protocol; no change to SandboxAction or executor governance.
- **Execution**: Uses host `podman` or `docker` (auto-detect). Mounts `working_dir` as `/workspace` in container; runs command in exec form (no shell); enforces timeout; `--rm`; policy validation (command allowlist, working_dir) before run.
- **Fail-closed**: If no container runtime found, or configured runtime binary missing, or run fails → driver raises `SandboxExecutionError`; executor records EXECUTED (failed). No fallback to host execution.

### Configuration / selection

- **create_sandbox_driver(kind="local_process" | "container", policy=..., image=..., runtime=...)**: Factory for choosing backend. Use with `SandboxExecutor(driver=create_sandbox_driver("container"))`.
- **Direct injection**: `SandboxExecutor(driver=ContainerSandboxDriver(image="...", policy=...))` for full control.

### DriverSpec

- **Not introduced.** The existing `run(command, working_dir, timeout_seconds=..., env=..., capture_artifacts=...)` signature is sufficient. Container-specific options (image, runtime binary, workspace mount path) are passed via `ContainerSandboxDriver` constructor. Adding a DriverSpec would not materially improve M3.11 and would broaden the driver contract unnecessarily.

## Isolation guarantees actually achieved

- **Workspace isolation**: Host `working_dir` is mounted read-write at `/workspace`; command runs with `-w /workspace`. No host filesystem access outside that mount (subject to container runtime behavior).
- **No shell**: Command executed in exec form; `shell=False` in subprocess.
- **Timeout**: Enforced via subprocess timeout (policy or argument).
- **No implicit host mutation**: Container is ephemeral (`--rm`); only the mounted workspace is visible for artifacts.
- **Resource limits**: Not added in this milestone; can be added later via runtime-specific flags (e.g. `--memory`, `--cpus`) if the constructor is extended.
- **Fail-closed**: Missing runtime or run failure does not execute on host; executor returns EXECUTED (failed) with error details.
