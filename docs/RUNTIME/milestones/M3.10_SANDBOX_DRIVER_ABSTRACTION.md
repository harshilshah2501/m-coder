# M3.10 — Sandbox Driver Abstraction

## Objective

Introduce a **pluggable sandbox driver abstraction** beneath the governed execution path so that:

- Current local/process execution continues to work unchanged.
- A future container runtime (M3.11) can plug in without re-architecting the executor.
- No governance bypass and no ledger contract regression.

The runtime (SandboxExecutor) retains:

- Authority and boundary enforcement
- Plan-Gate decisions
- Governed execution outcome contract (REFUSED / BLOCKED / EXECUTED)
- Ledger linkage

The driver does **not** own governance logic; it only performs run/validate.

## Design

### Driver interface

- **SandboxDriver** (Protocol): `run(command, working_dir, timeout_seconds=..., env=...) -> SandboxResult` and `validate_only(command, working_dir) -> tuple[bool, str]`. Implementations may raise `SandboxPolicyViolation`, `SandboxTimeout`, `SandboxExecutionError`.
- **LocalProcessSandboxDriver**: Wraps existing `SandboxRunner`; default backend when no driver is supplied.
- **SandboxExecutor**: Accepts optional `driver: SandboxDriver | None`; when `None`, uses `LocalProcessSandboxDriver(policy=self.policy)`. All outcome construction, ledger append, and callback invocation remain in the executor.

### Preserved semantics

- **REFUSED**: Handled by controller (e.g. no Plan-Gate / no executor); unchanged.
- **BLOCKED**: Driver raises `SandboxPolicyViolation` → executor produces `GovernedExecutionResult(outcome_type="blocked", ...)` and appends to ledger when `ledger_store` is set.
- **EXECUTED**: Driver returns `SandboxResult` → executor produces `GovernedExecutionResult(outcome_type="executed", ...)` and appends; same in-memory ledger emitter and store behavior as before.

### Compatibility

- Existing sandbox result contract (`SandboxResult`, `GovernedExecutionResult`) unchanged.
- Existing ledger behavior and `SandboxLedgerStore` contract unchanged.
- Existing tests (runner, executor, demo e2e, ledger store, transition executor) pass without modification.

## Migration notes for M3.11

- M3.11 can introduce a **ContainerSandboxDriver** (or similar) implementing `SandboxDriver`: `run` executes inside a container and returns a `SandboxResult`; `validate_only` may perform container-scoped validation. No change to executor governance or ledger logic required.
- Optional: a **DriverRequest** dataclass can be added later if container driver needs extra fields (e.g. image, resources); the current interface uses positional/keyword args only.
