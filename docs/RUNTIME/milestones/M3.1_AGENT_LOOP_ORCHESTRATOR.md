## 1. Overview

The Agent Loop Orchestrator is the runtime governor path for all agent execution flows. It implements the core runtime principle: **the model proposes, the runtime decides.**

The orchestrator owns:
- Task state management
- Transition execution
- Retry/iteration budgets
- Stop conditions
- Sandbox invocation
- Ledger linkage
- Deterministic replay

### 2.1 Component Hierarchy

### 2.2 Execution Flow

```
Request → LoopController
            │
            ├── Load TaskState
            ├── Validate transition (TransitionValidator)
            ├── Check budgets (BudgetPolicy)
            ├── Evaluate stop conditions (StopConditionPolicy)
            │
            ├── Execute transition handler
            │   ├── governance_to_context → ContextEngine
            │   ├── validated_to_sandbox → PlanGate → SandboxExecutor
            │   └── ...
            │
            ├── Update state
            ├── Emit journal entry
            └── Persist state
```

## 3. Loop Controller

### 3.1 Core Responsibilities

1. **State Loading**: Load task state from TaskStateStore
2. **Transition Validation**: Validate against transition_matrix.v0.1.json
3. **Guard Evaluation**: Evaluate guard conditions for transitions
4. **Handler Dispatch**: Execute transition-specific logic
5. **State Persistence**: Save updated state
6. **Journal Emission**: Record transitions for replay/audit

### 3.2 API

```python
from runtime.orchestrator import LoopController

controller = LoopController(
    store=TaskStateStore(),
    validator=TransitionValidator(),
    context_engine=ContextEngine(),
    sandbox_executor=SandboxExecutor(),
    ledger_store=SandboxLedgerStore(),
    plan_gate_service=PlanGateService(),
)

# Create task
state = controller.create_task("task-001", max_iterations=10)

# Apply transition
result = controller.apply_transition(
    "task-001",
    transition_id="task_to_plan_eval",
    guard_inputs={"event_valid": True},
)

# Get journal
journal = controller.get_journal()
```

### 3.3 Transition Wiring

| Transition | Handler | Service |
|------------|---------|---------|
| `task_to_plan_eval` | Validate event | — |
| `plan_eval_to_governance` | Plan-Gate checkpoint | PlanGateService |
| `governance_to_context` | Build context bundle | ContextEngine |
| `validated_to_sandbox` | Plan-Gate + Sandbox | PlanGateService, SandboxExecutor |

## 4. Transition Executor

### 4.1 Execution Phases

1. **Pre-validation**: Validate transition against matrix
2. **Budget Check**: Verify budgets not exhausted
3. **Stop Condition Check**: Evaluate stop conditions
4. **Guard Evaluation**: Check guard conditions
5. **Pre-hooks**: Run registered pre-execution hooks
6. **Handler Dispatch**: Execute transition handler
7. **Post-hooks**: Run registered post-execution hooks

### 4.2 Handler Registration

```python
from runtime.orchestrator import TransitionExecutor, TransitionHandlerResult

executor = TransitionExecutor()

def my_handler(task_id, from_state, to_state, guard_inputs, context):
    # Execute transition logic
    return TransitionHandlerResult.ok({"key": "value"})

executor.register_handler("my_transition", my_handler)
```

### 4.3 Hooks

```python
# Pre-hook: can abort execution by returning None
def pre_hook(context: ExecutionContext) -> ExecutionContext | None:
    if some_condition:
        return None  # Abort
    return context

# Post-hook: runs after successful execution
def post_hook(context: ExecutionContext, result: ExecutionResult) -> None:
    log_execution(context, result)

executor.register_pre_hook(pre_hook)
executor.register_post_hook(post_hook)
```

## 5. Budget Policy

### 5.1 Budget Types

| Type | Description | Limit |
|------|-------------|-------|
| `ITERATION` | Retry loop iterations | `max_iterations` (default 10) |
| `REPETITION` | Consecutive same transition | `max_consecutive_same_transition` (default 5) |
| `TOKEN` | Tokens consumed (future) | Configurable |
| `TIME` | Elapsed time (future) | Configurable |

### 5.2 Budget Configuration

```python
from runtime.orchestrator import BudgetPolicy, BudgetConfig

config = BudgetConfig(
    max_iterations=10,
    max_consecutive_same_transition=5,
    max_tokens=0,  # 0 = unlimited
    max_elapsed_seconds=0,  # 0 = unlimited
    warning_threshold_pct=80.0,
)

policy = BudgetPolicy(config)
result = policy.check_budgets(task_state_dict)

if not result.can_continue:
    # Budget exhausted
    print(result.block_reason)
```

### 5.3 Budget Enforcement

- Budgets are checked before each transition
- Exhausted budgets block the transition
- Warning thresholds trigger alerts without blocking
- All checks are fail-closed: ambiguity blocks

## 6. Stop Conditions

### 6.1 Stop Reason Categories

| Category | Reasons | Terminal State |
|----------|---------|----------------|
| **Governance** | explicit_refusal, boundary_block, authority_fail, boundary_crossed | COMPLETED (refusal), BLOCKED |
| **Loop** | budget_exhausted, iteration_limit, validation_failed | BLOCKED |
| **Execution** | sandbox_error, test_failure, timeout | FAILED |
| **User** | user_abort | ABORTED |

### 6.2 Stop Condition Evaluation

```python
from runtime.orchestrator import StopConditionPolicy, StopReason

policy = StopConditionPolicy()
result = policy.evaluate(task_state_dict, context)

if result.should_stop:
    print(f"Stop: {result.reason} → {result.terminal_state}")
    print(f"Message: {result.message}")
```

### 6.3 Force Terminal

```python
should_force, target_state = policy.should_force_terminal(
    current_state="GOVERNANCE_CLASSIFIED",
    stop_condition=result,
)

if should_force:
    # Force transition to target_state
    pass
```

## 9. Terminal State Rules

### 9.1 Non-Escaping States

These states have no outgoing transitions:
- `COMPLETED` — Task finished successfully
- `BLOCKED` — Task blocked by governance/loop condition
- `FAILED` — Task failed during execution
- `ABORTED` — Task aborted by user/system

### 9.2 Terminal State Enforcement

```python
if self.validator.is_terminal(from_state):
    return TransitionResult(
        valid=False,
        reason=f"Cannot transition from terminal state: {from_state}",
    )
```

## 10. Invariants

### 10.1 Runtime Invariants

1. **No bypass path**: All transitions flow through LoopController
2. **Fail-closed**: Validation failures block, not pass
3. **Terminal non-escaping**: Terminal states have no outgoing transitions
4. **Deterministic**: Same inputs → same state transitions
5. **Append-only journal**: Transitions recorded immutably

### 10.2 Governance Invariants

1. **REF dominance**: REF refusal cannot be overridden
2. **Authority required**: Sandbox requires authority check
3. **Boundary enforcement**: Boundary crossing requires Plan-Gate
4. **Model proposes, runtime decides**: No model-controlled transitions
