1. What a "task" is in the Layer-3 governed runtime architecture

## 3. What a Task Is in This Architecture

### 3.1 Definition

A **task** is a **runtime-owned, bounded unit of work** that:
1. Enters the governed agent loop via `TASK_RECEIVED`
2. Flows through the state machine under runtime control
3. Exits via a terminal state (`COMPLETED`, `BLOCKED`, `FAILED`, `ABORTED`)
4. May produce ledger evidence, context bundles, and execution artifacts
5. Can later be evaluated against governance and acceptance criteria (M3.18)

### 3.2 Ownership Principle

> The **runtime owns the task**. The model does not create, mutate, or terminate tasks. The model produces proposals within a task context; the runtime decides state transitions.

### 3.3 Task vs. Related Concepts

| Concept | What It Is | Relationship to Task |
|---------|------------|---------------------|
| **Task** | Runtime-owned bounded work unit | Primary identity |
| **Request** | Inbound payload (IDE, API, ingestion) | Task is created *from* a request; `request_id` is input linkage |
| **Plan** | Governance-evaluated structure (plan.v0.1) | Task *has* a plan; `plan_hash` links them |
| **State Row (TaskState)** | Current loop state + journal | Task schema *replaces/subsumes* the informal TaskState |
| **Ledger Row** | Append-only evidence record | Task *produces* ledger rows; `task_id` may appear in ledger |
| **Jira Issue / PR / Ingestion Artifact** | External work item | Task may be *sourced from* these; not the same thing |

### 3.4 Task Purpose Classification

A task schema is primarily:

| Facet | Yes/No | Notes |
|-------|--------|-------|
| **Execution-facing** | Yes | Drives state machine, sandbox, ledger |
| **Evaluation-facing** | Yes | M3.18 consumes tasks for harness evaluation |
| **Context-facing** | Yes | Context engine uses task_id |
| **Governance-facing** | Indirect | Task links to plan; plan carries governance classification |

Task schema is a **bridge** across execution, evaluation, and context — but governance classification remains in the plan.

## 4. Design Goals

The M3.17 Task Schema must be:

| Goal | Rationale |
|------|-----------|
| **Deterministic** | Same inputs produce identical task records; no hidden state |
| **Runtime-owned** | No model mutation; runtime controls lifecycle |
| **Governance-compatible** | Links to plan; does not redefine phase/boundary/authority semantics |
| **Minimal but sufficient** | Core fields only; no PM/work-management bloat |
| **Evaluation-ready** | M3.18 can consume tasks without restructuring |
| **Non-duplicative** | Does not replicate plan body, ledger rows, or doctrine |
| **Versioned** | `schema_version` field; migration path for future changes |
| **Validated** | JSON Schema + runtime validation; fail-closed on invalid |

## 5. Proposed Canonical Task Schema

### 5.1 Schema Surface

| Field | Type | Req? | Description | Rationale |
|-------|------|------|-------------|-----------|
| `schema_version` | `const: "task.v0.1"` | Yes | Schema version for validation and migration | All runtime schemas are versioned |
| `task_id` | `string` (UUID or prefixed ID) | Yes | Primary task identity; unique per runtime instance | Unambiguous linkage across all surfaces |
| `task_kind` | `enum` | Yes | Classification: `execution`, `ask`, `ingestion`, `evaluation` | Distinguishes runtime execution tasks from ask-only or ingestion tasks |
| `request_id` | `string` | Yes | Inbound request identifier (from IDE, API, ingestion) | Links task to originating request |
| `session_id` | `string` | Yes | Session/user context identifier | Matches plan.v0.1 and ledger_row.v0.1 |
| `source_surface` | `enum` | Yes | Origin surface: `ide_execute`, `ide_ask`, `api_execute`, `ingestion`, `replay` | Provenance for observability and routing |
| `repo_scope` | `object` | Yes | Repository targeting: `{ root_path, revision, branch? }` | Deterministic context; matches ContextRequest |
| `governance_ref` | `object` | No | Linkage to governance: `{ plan_hash?, expected_phase? }` | Connects to plan.v0.1 without duplicating plan body |
| `constraints` | `object` | No | Execution limits: `{ max_iterations?, budget_tokens?, timeout_seconds? }` | Fail-closed loop safety; matches LoopController |
| `acceptance_criteria` | `object` | No | Evaluation anchor: `{ description?, test_refs?, success_signals? }` | M3.18 evaluation surface; not full harness definition |
| `status` | `object` | Yes | Lifecycle state: `{ current_state, stop_reason?, terminal_at_utc? }` | Runtime state machine position |
| `created_at_utc` | `string (date-time)` | Yes | Task creation timestamp | Determinism and audit |
| `updated_at_utc` | `string (date-time)` | Yes | Last mutation timestamp | Audit and staleness detection |
| `provenance` | `object` | No | Creation context: `{ created_by, parent_task_id?, ingestion_batch_id? }` | Traceability for ingestion and multi-task workflows |
| `metadata` | `object` | No | Extension surface for runtime-specific data | Avoid schema churn for minor additions |

### 5.2 Proposed JSON Schema Structure

```
task.v0.1
├── schema_version (const)
├── task_id (required)
├── task_kind (required, enum)
├── request_id (required)
├── session_id (required)
├── source_surface (required, enum)
├── repo_scope (required)
│   ├── root_path (required)
│   ├── revision (required)
│   └── branch (optional)
├── governance_ref (optional)
│   ├── plan_hash (optional)
│   └── expected_phase (optional, enum: REF|CONF|DES|MIX|CODE)
├── constraints (optional)
│   ├── max_iterations (optional, integer)
│   ├── budget_tokens (optional, integer)
│   └── timeout_seconds (optional, integer)
├── acceptance_criteria (optional)
│   ├── description (optional, string)
│   ├── test_refs (optional, array of strings)
│   └── success_signals (optional, array of strings)
├── status (required)
│   ├── current_state (required, enum: agent_state)
│   ├── stop_reason (optional, enum: stop_reason)
│   └── terminal_at_utc (optional, date-time)
├── created_at_utc (required, date-time)
├── updated_at_utc (required, date-time)
├── provenance (optional)
│   ├── created_by (optional, string)
│   ├── parent_task_id (optional, string)
│   └── ingestion_batch_id (optional, string)
└── metadata (optional, object)
```

### 5.3 Enum Definitions

**task_kind**:
- `execution` — Governed runtime execution (IDE /v0/execute, API)
- `ask` — Plan-only ask (no sandbox execution)
- `ingestion` — Ingested from external source (Jira, PR, docs)
- `evaluation` — Created for M3.18 evaluation harness

**source_surface**:
- `ide_execute` — JetBrains/VS Code plugin execute action
- `ide_ask` — JetBrains/VS Code plugin ask action
- `api_execute` — API execute endpoint
- `ingestion` — M3.12–M3.16 ingestion pipeline
- `replay` — Ledger replay / deterministic reconstruction

**current_state**: Reuses `state_enums.v0.1.agent_state`

**stop_reason**: Reuses `state_enums.v0.1.stop_reason`

## 6. Schema Boundaries

### 6.1 What Belongs in Task Schema

| Belongs | Rationale |
|---------|-----------|
| Task identity (`task_id`, `task_kind`) | Primary contract surface |
| Request/session linkage | Joins to plan and ledger |
| Source surface provenance | Observability and routing |
| Repository scope | Deterministic context |
| Governance reference (hash, not body) | Links without duplication |
| Execution constraints | Fail-closed loop safety |
| Acceptance criteria (anchor) | M3.18 readiness |
| Lifecycle status | State machine position |
| Timestamps | Audit and determinism |
| Provenance metadata | Traceability |

### 6.2 What Does NOT Belong in Task Schema

| Does Not Belong | Reason | Where It Lives |
|-----------------|--------|----------------|
| Full plan body | Duplicative; plan.v0.1 is source of truth | `runtime/schemas/plan.v0.1.schema.json` |
| Full ledger rows | Duplicative; ledger is append-only evidence | `runtime/schemas/ledger_row.v0.1.schema.json` |
| Doctrine semantics (phase definitions, dominance) | Layer-1 concern | Layer-1 governance docs |
| Jira/PR/issue metadata | External PM system | Ingestion artifacts |
| Execution results as primary content | Results belong in ledger | Ledger + sandbox_ledger_store |
| Mutable free-form blobs without contract | Schema discipline | Use typed fields or metadata extension |
| Model reasoning / proposal content | Proposal is model-produced, not task | Model output surfaces |
| Full context bundle contents | ContextBundle is separate contract | `runtime/context/contracts.py` |
| Arbitrary work-management fields | Not runtime-relevant | External systems |

### 6.3 Boundary with Plan Schema

| Task Schema | Plan Schema |
|-------------|-------------|
| `governance_ref.plan_hash` (link) | Full plan body with all fields |
| `governance_ref.expected_phase` (hint) | `constitutional_phase_expected` (source of truth) |
| No authority/boundary fields | `authority`, `boundary`, `routing_invariants` |
| No policy_posture | `policy_posture`, `tooling_intent` |

The task **links to** the plan; it does not **contain** the plan.

### 6.4 Boundary with Ledger Schema

| Task Schema | Ledger Schema |
|-------------|---------------|
| `task_id` (may be emitted to ledger) | `event.request_id`, `event.session_id` |
| `status.current_state` (live) | `verdicts.terminal_posture` (captured at decision) |
| No verdict fields | `verdicts`, `boundary`, `actions`, `reason_codes` |
| No execution outcomes | `actions.tool_calls_attempted`, `actions.execution_intents` |

The task **produces** ledger rows; ledger rows **evidence** the task.

## 8. Lifecycle and Invariants

### 8.1 Creation

| Rule | Description |
|------|-------------|
| **Creator** | Runtime only; triggered by request arrival or ingestion |
| **When** | On `TASK_RECEIVED` state entry |
| **Required fields** | `schema_version`, `task_id`, `task_kind`, `request_id`, `session_id`, `source_surface`, `repo_scope`, `status`, timestamps |
| **Initial state** | `status.current_state = "TASK_RECEIVED"` |
| **Validation** | JSON Schema validation at creation; invalid → reject request |

### 8.2 Validity Rules

| Invariant | Enforcement |
|-----------|-------------|
| `task_id` is unique per runtime instance | Runtime-generated UUID or prefixed ID |
| `task_id` is immutable once set | No mutation allowed |
| `request_id` must reference valid inbound request | Validation at creation |
| `repo_scope.revision` must be non-empty | Schema required field |
| `status.current_state` must be valid `agent_state` | Enum validation |
| `status.stop_reason` only set in terminal states | Runtime-enforced |
| `governance_ref.plan_hash` if set must match existing plan | Validated at plan linkage |

### 8.3 Mutability Rules

| Field Category | Mutability |
|----------------|------------|
| Identity (`task_id`, `request_id`, `session_id`) | **Immutable** |
| Provenance (`source_surface`, `created_at_utc`, `provenance.*`) | **Immutable** |
| Scope (`repo_scope`) | **Immutable** |
| Governance linkage (`governance_ref.plan_hash`) | **Append-only** (set once when plan created) |
| Constraints | **Immutable** (set at creation or early lifecycle) |
| Acceptance criteria | **Append-only** (may add, not remove or change) |
| Status (`current_state`, `stop_reason`, `terminal_at_utc`) | **Runtime-mutable** (state machine drives) |
| `updated_at_utc` | **Always updated** on any mutation |
| `metadata` | **Runtime-mutable** (extension surface) |

### 8.4 Identity Rules

| Question | Answer |
|----------|--------|
| Are `task_id` and `request_id` both needed? | **Yes**. `task_id` is runtime-owned identity; `request_id` links to inbound request. A single request may spawn multiple tasks (future multi-task workflows), and a task may be created from non-request sources (ingestion, replay). |
| Uniqueness scope of `task_id` | Unique per runtime instance; no global registry assumed |
| `task_id` format | `task-<UUID>` or `task-<timestamp>-<short-hash>` |

### 8.5 Determinism Rules

| Rule | Rationale |
|------|-----------|
| Same request + same repo state → same task_id (except UUID portion) | Determinism for replay |
| Canonical JSON serialization (sorted keys, UTF-8) | Hash stability |
| No floating-point fields | Determinism |
| Timestamps in ISO-8601 UTC | Consistency |

### 8.6 Versioning

| Aspect | Rule |
|--------|------|
| `schema_version` field | Required; `const: "task.v0.1"` |
| Schema evolution | New versions (e.g., `task.v0.2`) require migration strategy |
| Backward compatibility | Older tasks remain valid until explicit deprecation |
| Validation | JSON Schema validation; fail-closed on invalid |

## 10. Risks and Open Questions

### 10.1 Task Granularity Ambiguity

**Question**: What is the granularity of a task?

**Options**:
1. One task per user request (coarse)
2. One task per loop iteration (fine)
3. One task per plan (medium)

**Recommendation**: One task per user request (Option 1). Sub-task decomposition can use `provenance.parent_task_id` if needed later.

**Risk**: If granularity is wrong, M3.18 harness may require restructuring.

### 10.2 Overlap with Plan Contract

**Question**: How much governance metadata should task carry vs. link to plan?

**Current position**: Task links to plan via `plan_hash`; does not duplicate plan fields.

**Risk**: If task-to-plan join is expensive or plan is not always available, task may need more governance fields.

**Mitigation**: Allow `governance_ref.expected_phase` as optional hint; full governance remains in plan.

### 10.3 Ingestion-Produced vs. Runtime-Created Tasks

**Question**: Do ingestion-produced tasks (M3.12–M3.16) have the same schema as runtime execution tasks?

**Current position**: Yes, same schema with `task_kind = "ingestion"`.

**Risk**: Ingestion tasks may have different lifecycle (no state machine traversal).

**Mitigation**: `task_kind` enum distinguishes; status may start as `TASK_RECEIVED` or a designated ingestion state.

### 10.4 Task Schema for Evaluation Tasks

**Question**: Should M3.18 evaluation harness create its own task kind?

**Current position**: Yes, `task_kind = "evaluation"`.

**Risk**: Evaluation tasks may need fields not in execution tasks (e.g., expected_outcome, test_harness_config).

**Mitigation**: Use `acceptance_criteria` and `metadata` for evaluation-specific fields; avoid overfitting now.

### 10.5 Evaluation Metadata Deferral

**Question**: How much evaluation metadata to include now vs. defer to M3.18?

**Current position**: Include minimal `acceptance_criteria` anchor; defer harness-specific fields.

**Risk**: M3.18 may require schema changes.

**Mitigation**: Schema versioning allows task.v0.2 if needed; `metadata` provides extension surface.

### 10.6 task_id vs. request_id Semantics

**Question**: Are both `task_id` and `request_id` necessary?

**Current position**: Yes.
- `request_id` = inbound request identifier (from client)
- `task_id` = runtime-owned task identity

**Rationale**:
- A single request may spawn multiple tasks (future)
- A task may be created without a request (ingestion, replay)
- Ledger join key remains `(request_id, plan_hash)`; task_id adds another join dimension

### 10.7 Terminal State Semantics

**Question**: When does `status.terminal_at_utc` get set?

**Answer**: When `current_state` transitions to a terminal state (`COMPLETED`, `BLOCKED`, `FAILED`, `ABORTED`).

**Invariant**: `terminal_at_utc` is set exactly once and never cleared.

### 10.8 Multi-Task Workflows

**Question**: Should M3.17 support parent/child task relationships?

**Current position**: Minimal support via `provenance.parent_task_id`; full multi-task orchestration is out of scope.

**Risk**: Ingestion may produce batches of related tasks.

**Mitigation**: `provenance.ingestion_batch_id` groups ingested tasks; parent_task_id for explicit hierarchy.

### 10.9 Schema Stability

**Question**: How stable must task.v0.1 be before M3.18?

**Requirement**: Core identity and status fields must be stable. Extension fields (metadata, acceptance_criteria) may evolve.

**Risk**: Early schema lock may miss M3.18 needs.

**Mitigation**: M3.18 planning pass should inform final schema before implementation.
